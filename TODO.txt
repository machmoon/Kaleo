[EXAMPLES OF PROMPTS]
These examples stay inside the emitter's current footprint set. That set is
now wider than the ban these lines used to carry, and the ban is gone: a
board with no way to get power in and no way to get signals out is not a
board anybody can build, which is what every prompt below was written around.

Supported today, by kind and package name (rendered in words by
`board.supported_packages_text()`, which is what the model is actually shown,
so this list is a copy and that function is the truth):

  kind 'ic'         SOT-223 (3 pins), SOIC (4/6/8/10/14/16/20/24/28),
                    LQFP (32/44/48/64/100/144), and the named plug-in modules
  kind 'connector'  Barrel_Jack_5.5x2.1mm, TerminalBlock_2P_5.08mm,
                    JST_PH_2P/3P/4P, PinHeader_1x02/03/04/05/06/08/10_P2.54mm,
                    USB_C_Receptacle_Power (6-way, power only)
  kind 'battery'    BatteryHolder_CR2032, BatteryHolder_AAA_1x
  kind 'switch'     SW_SPST_TL3305A (SMD tactile push button)
  kind 'testpoint'  TestPoint_Pad_1.5x1.5mm
  passives          two-terminal chip R/C/L/D/Y

Still out of demo requests, because nothing draws them: pin *sockets*, IDC and
ribbon headers, dual-row 2.54 mm headers other than the named modules, slide
and DIP switches, rotary encoders, relays, USB-A/micro/mini, RJ45, SD sockets,
Keystone test posts and loops, and any USB-C receptacle with data pins. A
request naming one of those is refused by `_footprint_for_device` with the
list above -- it does not silently become something else -- but a demo that
gets refused is still a demo that fails.

Two things a connector prompt should say out loud, because they are true of
what gets emitted: the USB-C receptacle's four shield tabs are **not** drawn
(they are 0.6 x 1.2 mm slots and `Pad` carries one round drill), so a real
build adds them by hand; and the tactile switch drawn is the TL3305**A**,
whose actuator is 3.8 mm -- see feature 29 below for what that costs the case.

- A minimal 3.3 V LDO regulator using an AMS1117-3.3 in SOT-223, with a
  10 uF input capacitor from VIN to GND and a 22 uF output capacitor from
  +3V3 to GND. Use only the regulator and passive components; do not add
  connectors, headers, switches, buttons, or test points.
- A roughly 1 Hz LED blinker using an NE555D in SOIC-8 on a +9 V rail, with
  astable timing resistors and capacitor, 100 nF supply decoupling, and one
  LED with a series current-limiting resistor. Use only the SOIC IC and
  two-terminal passives; do not add connectors, headers, or switches.
- A minimal ATtiny85-20SU board in SOIC-8 on a +5 V rail, with a 100 nF VCC
  decoupling capacitor, a 10 kOhm reset pull-up, and a status LED with a
  series resistor on PB1. Do not add an ISP header, connectors, buttons, or
  test points.
- A buffered 2.5 V reference on a +5 V rail using an LM358D in SOIC-8: two
  10 kOhm resistors form the divider, one amplifier is a voltage follower,
  the unused amplifier is tied to a defined state, and the supply has a
  100 nF decoupling capacitor. Do not add connectors or test points.
- Reviewer demo: an AMS1117-3.3 regulator in SOT-223 with a 10 uF input
  capacitor and a 22 uF ceramic output capacitor. Use only the regulator and
  passive components, and preserve the ceramic output-capacitor choice so the
  adversarial review can check it against the selected AMS1117 datasheet.
- Connector demo (the one a person can actually build and plug in): a 3.3 V
  supply board that takes power on a 5.5 x 2.1 mm barrel jack, regulates it
  with an AMS1117-3.3 in SOT-223 with a 10 uF input and 22 uF output
  capacitor, brings +3V3 and GND out on a 2-pin 5.08 mm screw terminal, and
  breaks +3V3, GND and two spare pins out on a 1x04 0.1 inch header. Add a
  1.5 mm test pad on +3V3.
- Connector demo, USB-C variant: the same 3.3 V supply taking power from a
  6-way power-only USB-C receptacle with the two 5.1 kOhm CC pull-downs to
  GND that make a charger deliver 5 V, an SMD tactile push button pulling a
  NRST net down against a 10 kOhm pull-up to +3V3, and a 1x04 header. Say in
  the request that the receptacle's shield tabs are added by hand.

STAGE 1, local listening. The only hard part is macOS system audio.
  The deleted app/src-tauri/src/speaker/ module had REAL implementations on
  Windows (WASAPI loopback) and Linux (Pulse .monitor). macOS was ALWAYS a
  stub: upstream used a CoreAudio process tap via `cidre`, whose build shells
  out to xcodebuild and so needs a full ~10 GB Xcode install. Today, on a call,
  Ada hears only what leaks from the speakers into the microphone.
  Two verified fixes:
    - screencapturekit crate 9.0.1 — system audio, macOS 13+, Command Line
      Tools only. Screen Recording is already granted (desk.rs shells out to
      `screencapture`). RECOMMENDED: lower OS floor, pure Rust.
    - CoreAudio process tap, macOS 14.2+, can tap a single pid. A complete
      working blueprint sits at vendor/openwhispr/resources/macos-audio-tap.swift
      — CLAUDE.md marks vendor read-only, so read the approach, write our own.
  Capture TWO TRACKS, not a mixdown: mic = you, system = them. That is the only
  diarization available, because transcribe_audio returns a flat string with no
  speaker labels by design.
  Three things that will bite:
    - Mic arbitration. wake/mic.rs Mic::open() is single-owner and the wake
      thread holds it; a 45-minute recording cannot coexist with an armed ear.
    - Clock drift. Mic and tap are separate clock domains and slide over an
      hour. resample_linear is a 2-tap interpolator with no anti-aliasing —
      fine for a wake spotter, not for long-form.
    - /transcribe is one-shot, <=1 MiB, <=60 s, 15 RPM. A 45-minute meeting is
      ~675 segments. Needs a purpose:"meeting" lane with its own pacer,
      following the existing WAKE_REQUEST_PACER precedent.

STAGE 3, guided cursor ("show me where to click"). Verified by string
  inspection of the installed KiCad 10.0.6:
    libwx_osx_cocoau-3.2.0.4.1.dylib   NSAccessibility  0
    _pcbnew.kiface                     NSAccessibility  0
    libwx_osx_cocoau-3.2.0.4.1.dylib   wxNSMenu 3, setMainMenu 1
    libwx_osx_cocoau-3.2.0.4.1.dylib   wxAuiToolBar 9
  So MENUS are precisely addressable through Accessibility (wx hands real
  NSMenus to [NSApp setMainMenu:], which gets AX for free from AppKit), while
  TOOLBARS and the GL canvas are owner-drawn and expose nothing. "How do I run
  DRC?" is answerable exactly (Inspect > Design Rules Checker); pointing at a
  toolbar button needs vision and is best-effort.
  The permission for synthetic clicks is PostEvent, NOT Accessibility — they
  are separate TCC buckets, and Apple DTS documents a case where Accessibility
  was granted and mouse events still did nothing. Call CGPreflightPostEventAccess
  / CGRequestPostEventAccess directly (already in Cargo.lock via
  objc2-core-graphics); tauri-plugin-macos-permissions 2.3.0 does not expose
  it, and the toggle only takes effect after a relaunch.
  Three coordinate frames are in play: desk.rs returns physical pixels, NSEvent
  is bottom-left points, CGEvent wants top-left points. Invisible to today's
  caption consumer, fatal for a 24 px button.
  Per-region click-through does not exist in Tauri (#2090 WONTFIX) and while a
  window ignores the cursor its webview receives no mouse events at all.
  Safety rule, extending this repo's own "a sentence never spends money":
  A SENTENCE NEVER TOUCHES THE BOARD. Never press a vision-derived target.

Prior art read: Clicky (farzaa) is an NSPanel menu-bar app; pointing is a
[POINT:x,y:label:screenN] marker in the model's own output, coordinates from
vision rather than an accessibility API, and the open-source version does not
click. Cluely is screen OCR + system audio -> STT -> LLM -> overlay; this repo
is a fork of Pluely, which is the open-source Cluely, so speaker/ WAS that
capture layer.
