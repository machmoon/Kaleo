The board file is the API

Decided

Most AI-and-KiCad tools are plugins: they live inside KiCad's Python environment and drive the IPC API, so they need KiCad running, a supported KiCad version, and a platform its plugin loader is happy on. We went the other way and parse the same S-expression format KiCad does. This is the thing that makes the demo survive a second user, and it's already built.

Open — pick one

Three ways to put a face on it

Ordered by how much has to be true for the demo to work. Each one already has an artboard, so the visual direction is not the unknown — the wiring is.

A

Review-only web view Review.dc.html

~4h build Low risk James

Paste a description, get back the findings list — blocker / marginal / note, each citing a datasheet page. No board canvas, no editing. A results page over the existing POST /generate.

For

It is the actual wedge. The DEVPOST argues semantic review is the underserved job, and this shows exactly that with nothing else in the way.

Against

Least visually impressive. No board, no motion, no "wow" frame for the video.

Fits in two days with room to spare. The endpoint already returns everything this needs.

B

Schematic + board viewer Main · Board.dc.html

~1.5 days Medium risk James + Ty

The Drafting Table app: KiCad's #F5F4EF schematic paper, with the placed board as an inset dark well showing real footprint positions from the solver, plus the review panel alongside.

For

Shows the whole pipeline in one frame — intent to placed board to cited review. Best single screenshot we can put on the submission.

Against

Needs a real renderer for footprints, pads, and courtyards from the .kicad_pcb. That is the part nobody has started, and it is where the two days go.

Doable only if the board render is scoped to rectangles + pads. No silkscreen art, no zones, no ratsnest. Courtyard outlines in #FF26E2 and pads in #C83434 read as a PCB well enough.

C

Overlay assistant + guided cursor Overlay · Teach.dc.html

3+ days High risk —

The floating Slew Rate assistant that sits over the user's real KiCad window and drives a ghost cursor to teach a control.

For

The most distinctive idea in the mockups, and the mascot and motion language are already designed.

Against

It needs to see and point at another app's window — screen capture, coordinate mapping, per-OS permissions. It is also the closest thing to the mouse-automation approach the DEVPOST explicitly disowns.

Recommend cutting for this deadline. It is the one that can fail on the judges' machine in a way we cannot debug live.

What I think we do

Build A, then B if A lands early. A is the argument the submission actually makes and it cannot fail on stage. B is the screenshot. C is a post-hackathon project.

  1. James — start on A. It is pure frontend over an existing endpoint, so no PCB knowledge needed anywhere in it.
  2. Ty — demo video and DEVPOST writeup, plus a clean-machine install from the README. If the install instructions are wrong, nothing else matters.
  3. Patrick — engine side, and the board render for B if A lands.

Disagree on any of it in the group chat — this is a proposal, not a decision.
